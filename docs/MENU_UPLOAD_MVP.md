# User-supplied menu fallback

When official-site discovery cannot corroborate the selected branch, a guest with a still-valid signed Google branch selection can upload a text-based PDF or HTML menu. An explicit upload accepts the unchanged, same-guest HMAC proof for up to 24 hours after selection; official website discovery still has a six-hour window and other checks remain shorter. This is a separate path from official website extraction. It uses the same HTML/PDF parsers, item evidence checks, price parser, menu versioning, signed snapshot permit, dietary/allergy exclusions, and mocked/approved Meta recommendation boundary.

The upload API is `POST /api/v2/menu-extraction/upload`, relayed through Next.js. It accepts one base64-encoded file up to 3 MB with the selected restaurant snapshot and guest-bound branch proof. The server detects the file signature and extension, never persists file bytes, and makes **zero** website, Google, or Meta requests. The response contains the file SHA-256, exact evidence quotes, PDF page numbers where available, and an `urn:dinetuned:upload:` source identity. A repeated request ID is rejected by the existing per-guest job ledger.

Upload parsing has its own bounded counters in the existing private SQLite job database (five per guest per hour and 30 globally per UTC day). Exhausting website-discovery requests does not block a local file upload, and no existing website counters are reset.

Uploaded files are labeled **user supplied, official origin and branch association unverified** throughout the menu and Picks. They cannot become official-site candidates through this endpoint. A document naming a different branch is rejected. Availability, dietary suitability, ingredients, and cross-contact remain unverified; existing hard safety exclusions still apply. Missing or ambiguous prices cannot enter Picks. The original file is not stored or publicly linked, so source quotes and hash remain visible in the current session, while a reload requires uploading again.

PNG, JPEG, WebP, and scanned PDF pages still need separately approved vision parsing. They produce no invented dishes. The normal real-Picks API remains disabled until an explicitly approved Meta test and later production dispatch gate. Offline fixture tests may use the mocked provider and must label it accordingly.

The model-bound context references a source registry once and links each eligible dish to its validated evidence ID. This keeps a 23-item, six-section uploaded menu under the existing 24 KB Meta request bound without dropping dishes, enlarging the output cap, or relaxing price/allergen checks. A bare `$` in a PDF does not establish USD; such prices remain visible in the menu but cannot enter Picks until a currency declaration is supported by the uploaded document. Any user-prepared transcription that adds a currency declaration must identify it as user-confirmed, never source-verified.

To test locally, keep the Google branch selection tab open, expand **Have a menu file or QR code instead?**, choose **Upload Menu**, select an authentic text PDF or saved HTML document, and press **Extract this menu file** once. Review the complete categorized result and its source notes before seeking Picks. No new official website request is needed for this upload path.
